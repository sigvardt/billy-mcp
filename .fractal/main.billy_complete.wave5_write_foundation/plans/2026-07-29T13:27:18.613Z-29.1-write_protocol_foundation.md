# 29.1 Ticketed write protocol foundation

## Goal

Deliver only the shared, process-volatile ticketed protocol in
`src/billy_mcp/api/write_protocol.py` and its focused unit tests.  The frozen
Wave-5 contract and cited Grok brief are the authority; no resource tool,
server, coverage, live, UI, bulk, or special-route work belongs here.

## Plan

1. Add strict Pydantic models for the preview result, ticket-only execute input,
   mapped execution result, and a frozen operation specification constrained to
   singular POST, PUT, and DELETE.  Canonicalise JSON-safe opaque payloads,
   percent-encode a non-empty item id, and build only the documented request
   shapes: rooted POST/PUT bodies and bodyless DELETE with an `{id}` ticket
   binding.
2. Implement `WriteProtocolService` around the existing locked
   `BillyHttpClient` and `ConfirmationStore`.  Preview issues a server-side
   binding plus volatile prepared-operation record without sending HTTP.
   Ticket-only execution consumes that exact binding before exactly one stored
   client request; it never accepts a caller business payload and relies on the
   client's write-no-retry behaviour.  Confirmation failures remain fixed,
   ticket-free `ToolError`s.
3. Map only operation-declared plural changed-record roots, preserving optional
   documented `meta.deletedRecords` when structurally valid and never creating
   it.  Require the primary changed-record list for POST/PUT and return a typed
   `VALIDATION_ERROR` for malformed success payloads; pass existing upstream
   `ToolError`s through unchanged.
4. Write MockTransport-only tests for canonical create/update/delete requests,
   preview non-mutation, one exact execution request/no retry, response and
   deleted-record mapping, malformed responses, 401/404 pass-through, strict
   model serialization, redaction, and the full confirmation matrix (tamper,
   tool/org/target/request/effect mismatches, replay, expiry, and concurrent
   double execute).
5. Run formatting, focused pytest, Ruff, Pyright, coverage/policy checks, and
   the node test script.  Record only durable implementation facts in memory,
   then commit the two owned files and node state after the later review step.

## Feasibility and boundaries

- Child capacity is `0/0/0`, so no delegation is possible or needed.
- Existing `ConfirmationStore` supplies 256-bit entropy, five-minute TTL, and
  atomic consumption.  Existing `BillyHttpClient.request` supplies locked-host
  transport and zero write retries; neither needs alteration.
- The current node memory is the only interrupted state: it records completed
  cited research and has no product implementation to resume.  Untracked seed
  runtime artifacts are outside the product scope and will not be staged.
