### Preview

`ui_products_create_preview` takes a strict Pydantic input (`extra=forbid`):

- `name` required, min length 1 (unique tagged names in live; offline may use a
  fixed `MCP-TEST-PRODUCT-*` tag)
- optional `account`, `salesTaxRuleset`, `unitPrice` matching the research163
  form, not an opaque API `product` blob

Call `protocol.preview` with:

- `execute_tool_name="ui_products_create_execute"`
- `target="products"`
- `canonical_request` = the validated fields
- `expected_effect_state` = `{action: create, resource: product}`
- summary that names a product create, not a submit

Return `UiWritePreviewResult`. Preview must not start a browser, click Gem, or
call the Billy HTTP API.

### Execute

`ui_products_create_execute` accepts only `confirmation_ticket` via
`UiWriteExecuteInput`. Consume with `execute_tool_name="ui_products_create_execute"`.
On success return a typed result built from the prepared payload (canonical
request plus expected effect). On protocol failure return the `ToolError`.

The register function receives only `FastMCP` and `UiWriteProtocol`. It cannot
gain a `BrowserRuntime` without editing `server.py`. Offline execute therefore
consumes the ticket and returns the bound request. It does not open a browser.

### Registration

Register both tools with `server.tool(...)` inside
`register_ui_product_write_tools`, same shape as `catalog_writes.py`. Keep
`ui_products_create_open` untouched.

## Offline tests (`tests/unit/test_ui_products_writes.py`)

Build a real `create_server` and qualify only through `server.call_tool`. Do not
call `BrowserRuntime` in these tests. Do not pass a fake submit service (the
register hook has no such seam).

Cover:

1. Preview no-submit: `ui_products_create_preview` returns a ticket and
   `canonical_request`; no `api.billysbilling.com` traffic (no HTTP client use).
2. Execute once: `ui_products_create_execute` with that ticket succeeds and
   echoes the previewed name.
3. Replay: second execute on the same ticket is `CONFIRMATION_CONSUMED`.
4. Expiry: advance a clock-injected `ConfirmationStore` past `MAX_TICKET_TTL`
   and expect `CONFIRMATION_EXPIRED`. If `create_server` does not accept a
   protocol/clock inject, construct `FastMCP()` and call
   `register_ui_product_write_tools` with a clocked `UiWriteProtocol` for the
   expiry case only. Still use `call_tool` as the proof.
5. Wrong tool: preview a product create, consume the ticket as
   `ui_products_create_execute` after registering a second consume under a
   different execute name on the same protocol, or preview then `call_tool` an
   execute that `consume`s as another tool name if one exists on this server.
   Practical path: issue a ticket bound to `ui_products_create_execute`, then
   `protocol.consume(..., execute_tool_name="ui_clients_create_execute")` is
   already covered in `test_ui_write_protocol.py`. Family test must still
   prove mismatch through this family's execute: preview with a protocol
   bound to a different execute tool name is not possible from the public
   preview tool. Instead, plant a ticket on the shared protocol via a second
   `register` is not available. Do this: create a bare FastMCP, register
   product tools, also issue `protocol.preview(execute_tool_name="ui_bills_create_execute", ...)`
   and `call_tool("ui_products_create_execute", {ticket})`. Expect
   `CONFIRMATION_MISMATCH`.

Also assert tool names exist on `create_server().list_tools()` and execute
input schema is only `confirmation_ticket`.

TDD: write the failing tests first, run them, then fill `products.py`.
