# 2.17 Wave-5a registration integration

## Decision

The completed `wave5a_root_registration` child is the only ready product
deliverable. Its committed tip `7cb74e2` changes the root registration,
offline-evidence generator, coverage artifacts, and registry test as one
coupled slice. The immediate work is therefore root integration and
qualification, followed by an independent Grok review. Wave-5b is deliberately
deferred: the cited research brief makes registration integration and a Grok
ACCEPT verdict its prerequisite.

The integration itself is a short, coupled parent task; splitting it would add
merge risk without independent ownership. The subsequent independent review is
both separable and mandatory, so it will be delegated to a focused `grok`
child after the parent has committed the integrated root baseline. No
Codex-Power Wave-5b implementation child will start until that review accepts
the registration slice.

   `main.billy_complete.wave5a_root_registration`. Remove only the merged

4. Regenerate and validate coverage. Only the frozen 15 clear CUD rows may

   tool names, every UI row remains red, and `complete` remains false.
5. Run `git diff --check`, formatter, Ruff, Pyright,
   `BILLY_TEST_MODE=commit bash .fractal/main.billy_complete/scripts/test.sh`,
   the coverage false-completeness checker, and repository-policy checks. Do

6. Commit and push the integrated root baseline before any reviewer is

## Independent review child

1. Initialise `wave5a_registration_review` from the committed root with
   `--agent=grok`, scope it to `wiki`, and give it exclusive ownership of
   `wiki/wave_fivea_root_registration_independent_review.md`.
2. Its contract is to independently re-fetch the current official Billy docs
   and cite them; inspect the integrated root and a clean archive; run focused
   registration/coverage tests; inspect every registered preview/execute schema
   and ticket-store sharing; and verify exact coverage inventory evidence.
3. The review must issue an explicit ACCEPT/FAIL verdict for the scoped
   registration product, keep live/UI/vision/bulk/special rows fail-closed, and
   state that product completeness is still false. It must not edit product
   code, coverage qualification flags, or child seeds.
4. If Grok fails before making any edit because of authentication, quota, or a
   rate limit, retry the full review through Codex Power as a non-authoritative
   fallback inspection. That fallback cannot substitute for the required Grok
   acceptance gate.
