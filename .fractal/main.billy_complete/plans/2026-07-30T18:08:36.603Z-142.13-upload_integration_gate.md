ticketed Wave-5s-B binary-upload implementation through archive-level root
verification. Keep all coverage fail-closed and open the mandatory independent
Grok audit only after a verified root merge.

  but its email and invoice-delivery product work is blocked by the Wave-5s-B

## Delegation decision

No new child is started now. The only runnable implementation surface overlaps
the active upload child, while the next two possible children are explicitly
gated: a `grok` independent reviewer requires the root upload merge, and a
`codex-power` Wave-5s-C builder requires that review's acceptance. Root work in
this cycle is therefore bounded integration preparation and validation.

## Execution sequence

1. Inspect the pending research82 root diff against `tmp/grok-research.md`; run
   `git diff --check`, `wiki update --path=wiki`, and `wiki lint --path=wiki`.
   Confirm it contains no raw probes, credentials, screenshots, or coverage
   greening. Keep the three write specials red and `complete: false`.
2. Inspect the upload child's updated three-dot diff and commit ancestry. Verify
   that its production changes are limited to the binary client, upload service,
   server registration, two inventory aliases, generator evidence, and focused
   tests. Recheck StrictBool parameters at the actual FastMCP boundary and
   CR/LF rejection before `httpx` transport.
3. Export the child tip with `git archive` into an owner-only temporary
   directory and execute its focused upload/client/registry/coverage tests,
   Ruff, Pyright, coverage generation, and false-completeness guard from those
   committed bytes. Verify exactly 182 offline implemented and contract-tested
   rows, zero live or vision rows, no UI or bulk greening, and `complete: false`.
4. Do not merge outside PREPARE. If the archive gate passes and the child has no
   unfinished material work, merge it at the next integration step with the
   required labelled no-fast-forward merge. Re-run the root non-live suite and
   coverage report after the merge, then unsave the upload-verification radio
   item.
5. After a successful root merge, create a read-only independent reviewer routed
   explicitly to `grok`. It must compare the merged bytes with the cited upload
   contract, recheck archive test evidence and coverage honesty, and publish a
   non-sensitive verdict. If Grok fails before edits because of authentication,
   quota, or rate limiting, repeat the full review with `codex-power` only as a
   non-authoritative fallback; retain the missing Grok audit as an open gate.
6. Only after Grok accepts the root upload product, initialise a disjoint
   `codex-power` Wave-5s-C implementation leaf for the two custom
   ConfirmationStore services. It must bind email and delivery tickets to the
   invoice id, bind delivery organisation to the payload, use only documented
   JSON routes and fields, and avoid inventing recipients, delivery reads,
   receiver-CVR fields, webhooks, or response roots.

  external email, e-invoice delivery, or coverage-complete claim is authorised
