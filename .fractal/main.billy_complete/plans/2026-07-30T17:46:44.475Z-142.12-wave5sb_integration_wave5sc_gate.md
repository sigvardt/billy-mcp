# 142.12 Wave-5s-B integration and Wave-5s-C gate

## Objective

Preserve the cited Wave-5s-C research handoff, integrate the already-active
Wave-5s-B binary-upload product only after archive-level verification, and
open the next invoice-email/e-invoice implementation gate without allowing
research, fallback review, or unauthenticated method probes to green coverage.

## Adopted state and authority

- The root worktree already contains an intentional, uncommitted Grok research81
  handoff: `tmp/grok-research.md`,
  `wiki/wave_fivesc_invoice_email_delivery_research.md`, residual-ranking
  pointers, memory, and the supporting research plan. The prior root commit is
  not a failed-step backstop, so this scratch brief remains the authoritative
  current research input for this iteration.
- Research81 rechecked the official docs body at MD5
  `8b94b0135c91fd15fe54ea33e088a4be`. It freezes only raw JSON POST
  `/invoices/:invoiceId/emails` and POST `/invoiceDeliveries`, with the typed
  preview/execute names recorded in the inventory. It establishes no live, UI,
  vision, bulk, response-body, or completeness evidence.
- `wave5sb_files_upload_product` is the only active child. It exclusively owns
  the binary client/upload service, its registration, coverage evidence, and
  upload tests. Its unmerged work must not be copied or modified from root.
- The next implementation gate is Wave-5s-C only after Wave-5s-B is merged and
  independently reviewed. Email must bind the invoice id as ticket target;
  delivery must validate only the documented GLN rule, never invent
  `receiverCvr`, delivery reads, a nested delivery path, or a webhook API.

## Delegation decision

No child is created during this step. The one current product child owns the
only runnable implementation slice, while the next slice is explicitly gated
on its merge and independent review. Spawning a second product child now would
create shared server/coverage/registry conflicts and violate that gate.

After integration, create a fresh, isolated `grok` reviewer for Wave-5s-B and
only then a `codex-power` Wave-5s-C product child. The former supplies the
required independent audit; the latter owns a new email/delivery module and
tests. If the Grok reviewer fails before edits due to authentication, quota, or
rate limiting, repeat the whole review with `codex-power` as the required
fallback record, while retaining the missing Grok review as an open gate.

## Execute sequence

1. Validate and retain research81 as root work in progress: inspect the full
   diff, run `git diff --check`, refresh/lint the project wiki, and confirm no
   coverage artifact, credential, raw probe output, screenshot, or browser
   evidence is tracked. Commit its durable cited pages with the next root
   integration commit; do not treat it as product evidence.
2. Monitor `main.billy_complete.wave5sb_files_upload_product`. When it exposes
   committed work, inspect `git diff main.billy_complete...<child>` and test a
   clean `git archive` checkout. Require its focused tests, registry count,
   two-row evidence (`api.special.files_upload` and `api.files.create`), binary
   request safety, and fail-closed coverage report before integration.
3. Merge only a verified Wave-5s-B child with
   `git merge --no-ff -m "merge main.billy_complete.wave5sb_files_upload_product"`.
   Run the merged offline suite and coverage generator. Require the expected
   offline +2, no live/vision change, no UI/bulk greening, and `complete: false`.
4. Spawn an independent post-merge product reviewer explicitly routed to
   `grok`. Its scope is read-only: compare the actual root merge against the
   cited upload handoff, inspect the archive test results and coverage output,
   then publish a non-sensitive reviewed verdict. A fallback reviewer may be
   recorded only under the pre-edit failure policy and cannot be called a Grok
   audit.
5. After the Wave-5s-B review is accepted, initialise a disjoint
   `codex-power` Wave-5s-C product leaf. Freeze its ownership to one new
   email/delivery write module, server registration, generator evidence for
   the two special rows, and focused contract tests. It must not touch upload
   code, generic confirmation semantics, or inventory rows beyond its two
   cited specials without escalation.
6. Require the Wave-5s-C leaf to implement two ticketed pairs only. Preview is
   mutation-free; execute accepts only the ticket. Email binds its nested
   invoice target and redacts body/subject. Delivery binds organisation and
   invoice identity, permits `cvr` without invented fields, and requires a
   13-digit GLN when `receiverIdType` is `gln`.

## Verification gates

- Research81: `git diff --check`, `wiki update --path=wiki`, `wiki lint
  --path=wiki`, credential/repository policy checks, and a tracked-file scan
  confirm that raw scratch evidence remains outside git.
- Wave-5s-B integration: clean-archive focused tests plus Ruff, Pyright,
  non-live unit/contract/safety checks, coverage generation, and an explicit
  failed `--require-complete` check for the remaining live/UI/bulk gates.
- Wave-5s-C product is not launched until post-merge review accepts the prior
  slice. Its future test matrix includes typed schemas, exact nested/flat JSON
  routes, no preview HTTP, one-shot ticket consumption, expiry, wrong executor,
  invoice/org/payload tampering, GLN validation, CVR omission, one-call failure
  behavior, and redaction.

## Non-claims

This plan does not approve an external email or e-invoice send, live test,
cleanup, UI workflow, vision review, invoice-delivery read/update/delete
operation, bulk operation, webhook, or project completeness. Coverage remains
fail-closed until real implementation and each required evidence class exists.
