# 142.14 Upload audit and exact-byte binding repair

## Objective

Close the Wave-5s-B product gate honestly: obtain the required independent
Grok audit of the merged upload implementation and repair the discovered gap
between the previewed digest and the bytes eventually supplied to the HTTP
client. This is a scoped offline safety increment; it cannot green live, UI,
vision, bulk, or overall completeness coverage.

## Baseline and delegation

1. Commit the current research83 findings, shared offline-write rule update,
   memory state, and these plans before any child is initialized. This gives
   every child the cited, committed contract it must inspect.
2. Create and start a Grok leaf `wave5sb_upload_product_review` with
   `--agent=grok`. It owns only
   `wiki/wave_fivesb_files_upload_product_independent_review.md`. It must
   independently review the merged code, contract, tool registration, ticket
   replay/expiry/organization binding, redaction, client base lock, and exact
   byte/digest semantics. Its review record must be non-sensitive, cite the
   official docs or existing cited handoff, identify every finding precisely,
   and say ACCEPT or FAIL; it must not edit product code or green coverage.
3. In parallel, create and start a Codex Power leaf
   `wave5sb_upload_race_fix` with `--agent=codex-power`. It owns only
   `src/billy_mcp/api/file_upload_writes.py` and
   `tests/api/test_file_upload_writes.py`. It must ensure the bytes handed to
   `BillyHttpClient.post_file` are hashed and compared to the preview ticket
   digest immediately before transport. A replacement or mutation before the
   read must fail `FILE_CHANGED` without any HTTP call; a mutation after a
   verified read cannot change the in-memory uploaded bytes. Add deterministic
   tests for that boundary, retain one-use ticket semantics, and run focused
   tests, format, lint, Pyright, coverage generation, and repository policy
   checks. It must not modify coverage state, server registration, or wiki.
4. When each child has a committed deliverable, inspect its three-dot diff and
   merge ready work with labelled `--no-ff` merges. Run the affected upload
   test suite on root. If the first Grok audit reports the expected race or any
   other defect, it remains a FAIL record; after the repair is merged, launch a
   fresh Grok follow-up audit against the repaired root before marking Wave-5s-B
   product accepted.
