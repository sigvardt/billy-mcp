# 2.19 Wave-5b root integration and independent review

## Objective

Integrate the completed, contract-frozen Wave-5b account and daybook-balance
ticketed-write leaves into the root server without changing any live, UI,
vision, bulk, or overall-completeness qualification state. Establish a clean
committed root baseline for an independent Grok product review before any
Wave-5c implementation begins.

## Decided ownership and gates

- Root (Codex Power lane): merge the two completed leaves, remove their merged
  Fractal child-seed directories as in the preceding Wave-5a integration,
  register the product modules, add the nine coverage evidence references,
  regenerate coverage, and run all offline verification.
- A fresh Grok child (after the root integration commit): independently review
  the committed root diff and cited Wave-5b contract. It owns no product files
  and must issue a durable PASS/ACCEPT or actionable findings; it may not mark
  live/UI/vision/bulk rows green.
- Wave-5c remains blocked: its cited daybook-transaction brief is ready, but
  no product work starts until this Wave-5b product review accepts the root
  integration.

## Execution plan

1. Review the exact three-dot product diffs and merge
   `main.billy_complete.wave5b_account_writes` and
   `main.billy_complete.wave5b_daybook_balance_writes` with labelled `--no-ff`
   merge commits. Preserve only the product code/tests after removing each
   merged child seed directory, matching the prior root integration cleanup.
2. Extend `src/billy_mcp/server.py` to import and register both leaf modules
   with the existing single `WriteProtocolService`; do not construct a second
   confirmation store or protocol. Update the root registry assertion from
   124 to 142 `api_*` tools and enumerate all 18 Wave-5b preview/execute names.
3. Add only the nine cited Wave-5b CUD entries to
   `OFFLINE_API_IMPLEMENTATION_EVIDENCE`, each pointing to its focused module
   contract suite and the root registry assertion. Regenerate checked-in
   coverage artifacts and verify exactly 118 implemented/contract-tested API
   rows, zero live rows, and `complete: false`.
4. Run `git diff --check`, formatter, Ruff, Pyright, focused Wave-5b tests,
   coverage-inventory tests, root registry tests, and the complete non-live
   suite. Confirm no credentials, browser evidence, or qualification shortcuts
   enter the tree.
5. Commit the verified root integration, then initialize and start a focused
   `--agent=grok` review child from that commit. Give it read-only ownership of
   the Wave-5b root diff and contract; require a cited durable review record
   with a defect-first verdict. Address any findings before accepting the gate.

## Success criteria for this iteration

- Server exposes 142 `api_*` tools plus the two coverage tools, including the
  exact 18 Wave-5b preview/execute names.
- The nine account-group, account, and daybook-balance-account rows are
  offline implemented/contract-tested only; all other red rows remain red.
- The root branch retains no newly merged Wave-5b child seed directory, no
  sensitive artifacts, and no unreviewed product claim.
- Grok product review is running from the committed root baseline or has
  returned a durable verdict; Wave-5c is not started prematurely.

## Post-Mortem

Both Wave-5b leaves were merged and their seed directories removed while their
product code and tests remained on root. The server registers all 18 tools;
coverage reports 118 implemented/contract-tested rows with zero live rows and
`complete: false`. The initial product acceptance was superseded when an
independent fallback review found P1 missing execute-tool identity and P2
unbounded terminal ticket/request retention. The repair passes an exact tool
name from all 24 execute handlers, rejects mismatches without HTTP, prunes
terminal state with clock-driven tests, and passes lint, type, coverage, policy,
and 650 non-live tests. A fresh Grok review is still required; Wave-5c remains
blocked and no browser evidence or credentials were added.
