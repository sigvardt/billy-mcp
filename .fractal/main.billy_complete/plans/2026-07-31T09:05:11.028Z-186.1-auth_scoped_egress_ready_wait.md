# 186.1 Auth-scoped browser egress and post-login auth_login_wait

## Goal

Unblock headless Billy browser login and classify the post-login shell under
research100 evidence, without greening live/vision coverage, without a new
`ui_*` tool, and without API-token read-back.

Cited authority: `.fractal/main.billy_complete/tmp/grok-research.md` (research100).

- Current `coverage/browser_egress.yaml` sets `api.billysbilling.com`
  `browser_action: deny`. Login form issues `POST /v2/user/login` to that host.
- Under deny, dual sessions stay on `/login` with send-failure error text.
- Research-only temporary allow yields dual-session
  `ready_shell_candidate` at path class `/:org_slug/dashboard` (no picker/MFA).
- Parent directive 07F2D101: derive test org identity from UI only; not a
  `BILLY_ORGANIZATION_ID` blocker; persist non-secret id **outside git**; no API.

## Design decisions

### 1. Path-scoped browser allow on the API host

Keep deny-by-default. Extend the egress policy beyond host-only allowlists.

**Manifest evolution** (backward-compatible intent):

- Keep host entries unique.
- For `mit.billy.dk` and `download.billy.dk`: unchanged `browser_action: allow`
  (full host, HTTPS only).
- For `api.billysbilling.com`: keep `api_client_action: exclusive_allow` and
  change browser handling to **path-scoped allow**, not full-host allow.
- Keep `api.billy.dk` fully denied for browser and API alias.

**Runtime `allows(url, method)`** (method from route request):

Allow browser traffic to `api.billysbilling.com` only when:

- scheme `https`, port default 443, host exact match, and
- method+path matches a reviewed rule table.

Initial path rules from research100 (minimal set that reached READY shell):

| Method | Path prefix / exact | Purpose |
| --- | --- | --- |
| POST | exact `/v2/user/login` | Credential submit |
| GET | `/v2/auth/` | Auth details |
| GET | exact `/v2/user` and `/v2/user/` | User document |
| GET | `/v2/user/bootstrap` | Bootstrap |
| GET | `/oauth2/tokeninfo` | Token info |
| GET | `/user/organizations` | Org list (browser session only; not API product) |
| GET | `/user/umbrellas` | Umbrellas |
| GET | `/v2/organizations/` | Org bootstrap/settings during shell settle |
| GET | `/organizations/` | Non-v2 org-scoped shell fetches |
| GET | `/e-invoicing/` | Observed shell load traffic |

Rules are prefix/exact only; never open arbitrary paths, never allow DELETE/PUT
except if later research proves a required auth-only method (none observed).

**Schema notes:**

- Prefer extending `BrowserEgressManifestHost` with optional
  `browser_path_allows: list[{methods: [...], match: "exact"|"prefix", path: str}]`
  and `browser_action: "deny" | "allow" | "path_allow"`.
- Fail closed if `path_allow` has empty rules.
- Bump evidence strings and test_references on the API host row.
- Keep `manifest: billy_browser_egress_phase_0` or bump only if validators force
  it; do not invent a second competing policy file.

This is **not** live API qualification. It must never set API inventory
`live_tested: true`.

### 2. Typed post-login observation on `auth_login_wait`

Keep tools:

- `auth_status` — unauthenticated login signature only → `AUTH_REQUIRED` or errors
  (unchanged meaning).
- `auth_login_start` — fill+click recorded controls → `AUTHENTICATING` (keep page
  close after submit is OK if cookies land on the persistent profile).
- `auth_login_wait` — **expand** to classify post-start state on the same
  MCP-owned persistent profile.

**Success model** (new or widened; name stable for MCP):

```text
AuthLoginWaitSuccess.status ∈ {
  AUTH_REQUIRED,   # login form still present
  READY            # shell path class observed
}
```

Prefer a dedicated `AuthLoginWaitSuccess` with
`status: Literal["AUTH_REQUIRED", "READY"]` rather than overloading
`AuthStatusSuccess` (which must stay login-only for `auth_status`).

**Classification order (fail closed):**

1. Known login signature on `/login` → `AUTH_REQUIRED`
   (optional: if send-failure error control present, still `AUTH_REQUIRED`;
   do not invent a new public code this slice unless tests need
   `BILLY_ERROR` for transport failure).
2. Path matches `^/[^/]+/dashboard$` on `mit.billy.dk`, login signature absent,
   and at least one non-PII shell marker (e.g. visible nav label class set
   from research: Overblik / Fakturering / Menu — exact frozen set in code
   comments citing research100) → `READY`.
3. Captcha / passkey / OTP controls if present →
   `ToolError(AUTH_INTERACTION_REQUIRED)` (wire detection, keep red until
   live-seen; unit-test with fakes).
4. Else → `UI_CHANGED` or redacted `BILLY_ERROR`.

**PII rules:** never return org slug, org name, person name, cookies, tokens,
or full URLs in tool output. Optional internal write of UI-derived org slug to
owner-only path outside git (e.g. under `~/.local/share/billy-mcp/`) for later
equality checks per parent directive — not in repo, not in MCP response.

### 3. Offline tests first; live probe second

Offline (must pass before commit):

- Egress matrix: mit allow; api deny for non-rule path; api allow for
  `POST /v2/user/login`; api.billy.dk deny; http deny; port deny.
- Manifest load failure still `EGRESS_DENIED` / load error.
- `auth_login_wait` READY via fake page with dashboard path + shell markers.
- `auth_login_wait` AUTH_REQUIRED via known login page.
- `auth_login_wait` UI_CHANGED on drift.
- No secret leakage in messages/`details`.
- Existing auth_status / auth_login_start tests still pass.

Live (execute step, credentials present; keep coverage flags red):

- Real headless: `auth_status` → start → wait → expect READY.
- Second independent ephemeral session (or second wait after fresh login) agrees
  on READY class.
- Derive org slug from path; persist outside git only.
- No frames in git; any vision frames owner-only and purged after review later.

### 4. Coverage honesty

- Do not mark UI rows live/vision green.
- Do not mark API rows live green; keep/add `out_of_scope_by_user` where the
  generator already supports it.
- Optionally update `coverage/status.json` / report blocker text so it no longer
  claims “BILLY_API_TOKEN unavailable” as the sole UI blocker (token is not
  required for UI qualification under user scope). Prefer generator-driven
  update if one exists; otherwise a minimal honest blocker string.
