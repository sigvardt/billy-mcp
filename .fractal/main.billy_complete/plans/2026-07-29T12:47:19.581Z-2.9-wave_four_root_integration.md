Integrate the frozen Wave-4 clear-read surface only after both active leaves
commit their file-isolated deliveries. Register all fifty Wave-4 get/list tools,
advance exactly their offline implementation and contract-test evidence, and
request a fresh Grok review. Preserve the fail-closed boundary: zero live or UI
qualification, zero write or bulk tools, and `complete: false`.

The governing contract is `.fractal/main.billy_complete/tmp/grok-research.md`
and `wiki/wave_four_remaining_clear_reads_contract.md`: official docs ETag
`hsisik4g9p3603`, MD5 `c2efda0ee4cf9cf200e14910c5fc6996`; `countryId` is
required only on cities, states, and zipcodes lists; each get supports typed
`RECORD_NOT_FOUND`; and the server must expose 94 `api_*` plus two
`coverage_*` tools after integration.

## Delegation decision

No new child is started. The two available leaves already own the only
file-disjoint implementation work. Root registration, redaction coverage,
generated evidence, the exact registry assertion, and post-merge verification
share the same files and must land atomically; splitting them would create
avoidable merge conflicts and weaken the evidence chain. A Grok review is
deferred until that concrete merged surface exists, as required by the cited
brief.

## Integration sequence

1. Wait for each active child to commit only its two owned product files.
   Inspect `git diff main.billy_complete...<child>`, `git diff --check`, and
   run its focused tests from a clean `git archive`; reject seed/runtime
   artifacts or any coverage, server, live, or UI change. Merge accepted work
   with labelled `--no-ff` merges and announce each material integration.
2. Add the five Wave-4 registration calls to `src/billy_mcp/server.py`:
   geo, tax, bank, balance/invoice extensions, and ledger/users. Extend
   `tests/unit/test_coverage_server.py` to assert the exact 94 API tool names
   plus both coverage tools and verify flat structured input schemas.
3. Add exactly fifty entries to
   `scripts/generate_coverage_report.py`'s
   `OFFLINE_API_IMPLEMENTATION_EVIDENCE`, each tied to its focused contract
   suite and the root registry test. Regenerate `coverage/api_v2_manifest.yaml`,
   `coverage/status.json`, and `coverage/report.md`. Verify exactly 94 API rows
   are `implemented` and `contract_tested`, all `live_tested` values remain
   false, all UI/vision rows remain red, and `complete` remains false.
4. Extend root redaction regression coverage for bank identifiers, reminder
   download URLs, and user email/phone diagnostics without changing successful
   structured tool content. Ensure get tools preserve typed 404
   `RECORD_NOT_FOUND` and list tools preserve 401 `AUTH_REQUIRED` mappings.
5. Run formatting, Ruff, Pyright, the full non-live suite, coverage generation
   and fail-closed coverage/policy checks. Run full mode only to prove it fails
   at the completeness gate while credentials and qualification evidence remain
   absent. Do not describe that expected failure as a passing qualification.
6. After root verification, request an independent Grok review of the exact
   merged archive. Address every concrete discrepancy before opening the next
   write/auth/live/UI wave.

## Acceptance boundary

- Exactly 50 real, typed Wave-4 get/list tools are added to the pre-existing
  44, for 94 API tools total; no generic HTTP/browser control or stub exists.
- Geo list inputs require non-blank `countryId`; no other Wave-4 list gains an
  invented filter or `offset`.
- Coverage becomes only offline-green for those fifty rows: no live, UI,
  vision, write, bulk, special-route, or completeness claim advances.
- The final integration has a clean archive, no credentials or raw evidence,
  and a fresh cited Grok review record.
