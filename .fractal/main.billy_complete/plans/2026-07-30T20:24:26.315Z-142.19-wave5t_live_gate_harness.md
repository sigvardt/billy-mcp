# 142.19 Wave-5t live residual and bulk gate harness

## Objective

Turn the cited Research88 result into one bounded, fail-closed live
qualification harness, then pivot the frontier to headless UI/auth discovery.
Neither stream may add residual or bulk MCP tools or improve coverage status
without successful dedicated-organisation evidence.

## Evidence and fixed boundaries

- Research88 is the implementation prerequisite: its primary official source
  is `https://www.billy.dk/api/`, fetched with ETag `"wcw4x9hqvu3603"`,
  147934 bytes, MD5 `8b94b0135c91fd15fe54ea33e088a4be`.
- The fixed API base is `https://api.billysbilling.com/v2`. The 29 residual
  clear rows and 92 bulk rows remain red. The unauthenticated `PUT
  /{resource}/bulk` result is a candidate only; PATCH collection meta-200 is
  never a contract.
- `BILLY_API_TOKEN` and organisation identity are unavailable in this
  environment. The no-token path must be explicit, exit successfully, produce
  no network activity, retain no secret, and leave all coverage fields false.
- A token path must reject an absent explicit non-production organisation
  designation, allow only the fixed Billy base, create only uniquely tagged
  disposable data after an observation has proved it is safe, delete in reverse
  dependency order, independently read back cleanup, and write only
  non-sensitive owner-only temporary evidence.
- The live-gate harness sub-slice excludes external email, e-invoice,
  UI/browser writes, screenshot/HAR/trace, bulk FastMCP tools, webhooks, and
  coverage greening. The parallel UI discovery stream remains read-only and
  headless.
- The parent direction makes the UI lane the next product frontier after this
  one harness. UI discovery must use the MCP-owned persistent profile in
  headless mode only, expose no generic browser controls, retain no raw frames,
  and report `AUTH_INTERACTION_REQUIRED` only for a verified unautomatable
  challenge.

## Decomposition decision

The work has two independent seams after the evidence baseline is frozen: one
Codex Power live-gate harness and one Grok UI/auth exploration. The Research88
brief already supplies the cited API prerequisite; Grok must supply the UI
brief before Codex Power writes UI workflows. Do not spawn either leaf until
the current research wiki and memory edits are committed; children must fork
the frozen evidence rather than an uncommitted workspace. After each product
merge, create a fresh Grok review from its merge commit.

## Execution plan

1. Validate and preserve the current Research88 wiki, memory, and probe-rule
   changes. Run wiki lint, the offline coverage checker, repository policy
   scan, formatting, Ruff, Pyright, and the non-live test suite. Commit the
   evidence baseline before a child is initialised.
2. Initialise a `codex-power` leaf named `wave5t_live_gate_harness` from that
   committed root. Its exclusive source ownership is
   `src/billy_mcp/live_probe.py`, `scripts/run_live_probe.py`, and
   `tests/live/test_live_probe.py` (plus a new focused unit-test file if it
   needs one). It may not edit API tools, coverage manifests/status, browser
   code, or shared node seed. Its deliverable is a typed/testable harness with
   a deterministic no-token/no-network report and a deliberately guarded live
   path; it must keep test data and raw evidence outside the repository.
3. In parallel, initialise a `grok` leaf named `wave5t_ui_auth_discovery` from
   the same committed root. It owns only its new UI/auth discovery wiki page,
   plan, and memory record. It must inspect the existing MCP-owned persistent
   browser profile and the headless login/auth state through bounded Billy
   hosts, identify API-to-UI parity entry points and interface-only workflows,
   and produce a cited brief. If credentials, organisation selection, CAPTCHA,
   passkey, push approval, or another challenge blocks it, it must record the
   exact observed state and recovery prerequisite without inventing success,
   retaining raw evidence, or changing coverage.
4. Verify the finished harness leaf from a clean `git archive`, inspect its
   three-dot diff against root, run its focused tests, then run the root
   non-live verification set. Merge only a passing, scoped child with a
   labelled no-fast-forward merge. Coverage must still report 184 implemented
   and contract-tested API rows, zero live/vision rows, and `complete: false`.
5. After the UI discovery brief is independently archived on root, initialise a
   bounded `codex-power` UI-auth/discovery implementation leaf. It may only
   own the specific UI/auth modules and tests named by the Grok brief. It must
   implement real typed `auth_*`/`ui_*` workflows rather than generic browser
   controls, remain headless, and keep all UI rows red unless DOM assertions,
   independent read-back, cleanup, and Grok vision review are actually
   complete. If discovery proves interaction is required, implement only the
   exact stable failure/recovery path supported by that evidence.
6. Verify each finished product leaf from a clean `git archive`, inspect its
   three-dot diff against root, run its focused tests, then run the root
   non-live verification set. Merge only a passing, scoped child with a
   labelled no-fast-forward merge. Coverage must still report 184 implemented
   and contract-tested API rows, zero live/vision rows, and `complete: false`.
7. Initialise a fresh `grok` leaf for an independent review of each merged
   product deliverable. It owns only its review plan/wiki/memory record, must
   re-check the cited official evidence and fail-closed paths, and may accept a
   harness only as infrastructure/research or a UI/auth path only to the extent
   it is tested. It may not claim live success or completeness.
8. If a review finds a defect, send the correction to a new focused
   `codex-power` leaf and repeat archive verification and independent Grok
   review. If it accepts, record the infrastructure/UI discovery verdict and
   preserve the token/org/browser-credential gates for later qualification.

## Completion criteria for this iteration

- Research88 is committed as a clean, linted shared record with no credential
  or raw probe artifact committed.
- The Codex Power harness and Grok UI/auth discovery work are configured
  against that committed baseline, with their non-overlapping ownership and
  non-claims explicit.
- No API/UI coverage row is advanced merely by scaffolding or research.
