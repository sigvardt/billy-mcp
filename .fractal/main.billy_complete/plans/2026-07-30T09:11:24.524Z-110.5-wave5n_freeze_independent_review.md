# 110.5 Wave-5n freeze independent review

## Objective

Obtain the required independent Grok verdict on the merged
`wiki/wave_fiven_ticketed_writes_contract.md` before any invoice-late-fee
product implementation can begin. Preserve the research61 evidence updates as
offline-only documentation; this iteration must not implement or green product
coverage.

## Evidence and gate

- Research61 in `.fractal/main.billy_complete/tmp/grok-research.md` cites the
  current official Billy docs and confirms the plain contract is unchanged.
- The frozen root page authorises only singular `invoiceLateFees` create and
  update, and explicitly excludes delete and both bulk rows.
- `POST` and `PUT` are auth-gated with a JSON-object body; singular and bulk
  `DELETE` are 405. This permits no live or UI claim.
- The Wave-5m product acceptance is a prerequisite for authoring the freeze,
  not a substitute for the required Wave-5n freeze review.

## Delegation decision

This review needs a clean, independent context and the design assigns it to
Grok. In EXECUTE, create one child leaf routed explicitly with `--agent=grok`,
named `wave5n_freeze_independent_review`, scoped to `wiki`, and grant it sole
ownership of `wiki/wave_fiven_freeze_independent_review.md` plus generated
index entries. Its completion criterion is an evidence-backed ACCEPT or a
specific repair verdict, not a product change. No Codex fallback is authorised
unless Grok fails before edits because of authentication, quota, or rate limit;
then retry the complete review with `--agent=codex-power` and label it
non-authoritative.

## Execution sequence

1. Keep the research61 state, probe-rule, and handoff-plan edits intact; check
   their diff for the cited HTTP fingerprint, `{}` body-gate clarification, and
   continued fail-closed coverage language. Run the applicable wiki and
   repository checks, then commit that evidence and this plan before spawning
   so the reviewer forks the actual root baseline rather than a stale commit.
2. Configure and launch the Grok review leaf from the committed root baseline.
   Its instructions must require a fresh official-doc comparison, review of the
   frozen page against research61 and the manifest, and a durable, non-sensitive
   wiki record. It must not modify source, tests, inventories, coverage status,
   credentials, browser data, or the frozen contract page.
3. Monitor the child. If it returns ACCEPT, merge and validate the review record
   and retain the product slice as the next gated action. If it returns a repair
   verdict, merge only the review record, plan the repair, and do not spawn the
   product child.
4. After any merge, run `wiki lint`, check the index, verify the root still has
   250 `api_*` tools and 172 offline implemented/contract-tested rows with
   `complete: false`, and scan the delivered diff for credentials or raw
   evidence.

## Success criteria

- Research61 updates are documented and remain fail-closed.
- A valid Grok independent freeze review is underway or merged, with no product
  implementation started early.
- The only possible next implementation after a Grok ACCEPT is the bounded
  four-tool `invoiceLateFees` create/update slice; delete, bulk, UI, live, and
  vision remain out of scope.
