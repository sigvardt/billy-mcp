# 142.22 Auth status integration and next UI-auth slices

## Objective

Integrate the bounded, corrected `auth_status` implementation without changing
coverage status, obtain the required independent Grok review, and prepare the
next credential/login/organisation work from current cited evidence.

## Evidence and non-negotiable boundaries

- Treat `.fractal/main.billy_complete/tmp/grok-research.md` research91 as the
  current cited contract for the known unauthenticated state: fixed
  `https://mit.billy.dk/` navigation; final `https://mit.billy.dk/login` with
  no query or fragment; email/password/remember controls; exactly one visible
  `button[data-cy="login-button"]` with exact `Log in` or `Log ind` text.
- Reject `button[type="submit"]` and `form button`: the observed login DOM has
  no form and no submit `type` attribute. Unknown route, count, visibility, or
  label must stay fail-closed as `UI_CHANGED`.
- Preserve headless-only runtime, exact browser allowlist, Pydantic-only tool
  boundary, redacted errors, and the ban on generic navigation/selector/click/
  type/DOM tools. `AUTH_INTERACTION_REQUIRED` is not valid for the observed
  credential-absent login screen.
- Keep all 339 UI rows red and all API coverage state unchanged. This slice is
  an offline typed implementation, not live UI qualification, independent
  read-back, vision verification, or a login submission.
- Residual and bulk candidates remain blocked before networking. Do not open a
  new API observation, write, or bulk implementation wave in this work.

## Execution plan

1. Wait for `main.billy_complete.ui_auth_status` to reach a committed terminal
   state. Inspect its committed diff and a clean `git archive` checkout; reject
   generated node artifacts, coverage edits, generic browser controls, and any
   behaviour outside the narrow source/test ownership.
2. Selectively integrate only the reviewed source and test changes plus the
   current root research91 state record. Verify format, Ruff, Pyright, coverage
   and repository-policy checks, focused auth tests, and the complete
   non-live suite before committing. The child’s seed and transient evidence
   never enter the root branch.
3. After the source baseline is merged, spawn a read-only `grok` leaf for an
   independent defect-first review. Its recorded review must compare the actual
   merged diff with research91 and the approved design, test corrected selector
   behaviour, registration/output schemas, headless/egress/redaction controls,
   and the unchanged red coverage posture. It may write only its review record
   under `wiki/`; it must not claim vision or live qualification.
4. In parallel with that review, spawn a `grok` research leaf for the next UI
   lane: secure credential resolution, the typed login transition, and
   organisation selection. It must produce a cited contract/discovery brief,
   distinguish documented inputs from observed DOM states, specify automated vs
   `AUTH_INTERACTION_REQUIRED` challenges, and leave all post-login UI rows
   red without non-production credentials. It must not implement a tool.
5. If the independent review finds a defect, spawn a scoped `codex-power` fix
   leaf, rerun verification, and obtain a fresh Grok re-review. If accepted,
   integrate the review and research records, then use their contracts to plan
   the credential/login/organisation implementation leaves.

## Decomposition decision

No new leaf starts during this PLAN step: the implementation child is still
finishing, and both planned Grok tasks need its committed, merged code as their
review/research baseline. Once that dependency clears, the independent review
and next-slice research are separable and will run concurrently with explicit
`--agent=grok` routes. A later repair, only if a finding exists, is delegated
to `--agent=codex-power` with source/test-only ownership.

## Acceptance checks for this phase

- The integrated `auth_status` recognises only the research91 login signature
  as typed `AUTH_REQUIRED` and returns typed `UI_CHANGED` for all drift.
- The root has no browser evidence, credentials, screenshots, frames, traces,
  HAR files, or coverage greening.
- Grok records an independent review verdict and a cited credential/login/org
  planning brief; neither record substitutes for live or vision qualification.
- The root branch remains clean and pushed after each integration.
