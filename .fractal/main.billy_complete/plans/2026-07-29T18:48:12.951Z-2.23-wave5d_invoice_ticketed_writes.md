## Frozen implementation contract

- Parent invoice routes are `POST /invoices`, `PUT /invoices/:id`, and
  bodyless `DELETE /invoices/:id`, using singular request root `invoice` and
  primary response root `invoices`.
- Invoice-line routes use the corresponding `/invoiceLines` endpoints and
  singular root `invoiceLine`; their `WriteOperationSpec` must declare
  `additional_plural_roots=("invoices",)`. The parent root is optional in a
  response but, when present, maps into `changed_records["invoices"]`.
- Both leaves use opaque inner payload dictionaries and strict outer Pydantic
  models. Each execute handler accepts only `confirmation_ticket`.
- Every preview binds a non-empty, handler-owned exact execute name, and every
  execute call passes that same name to the one shared `WriteProtocolService`.
  No request has a write retry; no child creates another confirmation store.
- Embedded invoice lines are documented as create-only, atomic, and at least
  one line, but offline payloads stay opaque. Do not infer live validation,
  implement bulk operations, or create external invoice special tools.

## Leaf acceptance checks

Each leaf follows the Wave-5c module pattern and proves, in its own focused
tests:

1. Exact flat registered names and typed input/output/error models.
2. Preview makes no HTTP call and canonicalises the exact singular-root request
   (or the delete `id` binding).
3. Execute sends the exact method, collection path, and request body once;
   deletes have no body.
4. Tampered, expired, replayed, wrong-organisation, wrong-target, and
   wrong-payload tickets fail without a write; same-module executor mismatch
   fails before ticket consumption and HTTP.
5. Empty token, authentication, and not-found errors stay typed. Line tests
   additionally cover both primary-only and primary-plus-parent multi-root
   successes without fabricating `invoices` when absent.
