# 2.2 Phase 0 integration and UI discovery handoff

## Objective

Integrate the reviewed Phase 0 coverage and safety-foundation deliverables,
preserve the refreshed Grok contract record, and set up the first bounded
headless interface-discovery handoff. This is not a completeness claim: all
coverage remains red until live non-production and UI evidence exists.

## Adopted state

- The uncommitted memory and API research-seed updates are a current Grok
  contract refresh. Preserve them with the integration work; the official API
  fingerprint is unchanged.
- `coverage_inventory` has reported a 305-row API manifest and 339 red UI rows.
  Before it commits, its duplicate `POST /v2/files` planned-tool mapping must
  be reconciled to the single multipart `api_files_upload_{preview,execute}`
  family (or an explicit alias). No JSON files-create tool is permitted.
- `shared_foundation` has reported the typed coverage-only FastMCP foundation.
  Its integration may not register planned API/UI stubs.
- `BILLY_API_TOKEN` and dedicated non-production organisation access remain
  unavailable, so live, bulk, UI, and vision coverage remain visibly false.

## Execution plan

1. Steer the coverage child to repair the documented files-upload alias before
   its commit. Let both children finish their own checks and commits; retain
   their radio reports in the saved queue until merged.
2. For each committed child branch, inspect the three-dot diff and confirm its
   ownership boundary. Validate executable artifacts from a clean `git archive`
   checkout before merging with a labelled no-fast-forward merge.
3. Reconcile coverage/manifest and foundation interfaces on the root branch:
   verify `coverage/status.json` is `complete: false`, all red/ambiguous rows
   remain red, the stdio entry point imports, coverage tools are the only
   registered tools, and the API/browser host locks have tests.
4. Run formatting, lint, Pyright, unit/contract tests, policy and dependency
   checks. Confirm the full qualification command fails closed only because
   coverage is incomplete; it must never soft-pass.
5. Once the foundation is merged, initialise a dedicated `--agent=grok`
   read-only UI-discovery child with ownership limited to interface evidence,
   review records, and shared wiki updates. It must use a headless persistent
   profile and return cited findings; lack of credentials or a challenge is a
   blocker, never a green row. Do not start a duplicate docs-research child:
   the refreshed cited brief already covers the next API-read slice.
6. Update the root wiki/memory with only durable merged facts, unsave each
   integrated child report, and report the integration result through radio.

- API manifest arithmetic is 207 clear operations, 92 individually ambiguous
  bulk operations, and six special routes; UI seeds stay discovered false.

## Delegation decision

The two independently deep implementation areas are already owned by focused
Codex Power children. Root integration is serial because their manifest and
tool-registry contracts meet at the merge. A third child is reserved for Grok
interface discovery after the headless foundation is present; spawning it
earlier would duplicate the existing documentation research and cannot inspect
the authenticated interface safely.
