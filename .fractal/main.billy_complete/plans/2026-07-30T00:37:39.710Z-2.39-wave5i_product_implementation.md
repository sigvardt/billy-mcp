# 2.39 Wave-5i sales-tax account and meta-field product

## Adopted evidence and scope

The current cited Grok product-ready brief at
`.fractal/main.billy_complete/tmp/grok-research.md` re-fetched the unchanged
official Billy API documentation (ETag `hsisik4g9p3603`, MD5
`c2efda0ee4cf9cf200e14910c5fc6996`). Its twelve-tool product handoff is
bounded by the accepted freeze contract at
`wiki/wave_fivei_ticketed_writes_contract.md` and its authoritative independent
freeze acceptance at `wiki/wave_fivei_freeze_independent_review.md`.

Implement only these six singular CUD operations, each with one preview and one
execute tool:

- `salesTaxAccounts`: create, update, delete;
- `salesTaxMetaFields`: create, update, delete.

Both families use client-relative paths, opaque inner payloads, strict outer
Pydantic models, one shared confirmation store/protocol, and no additional
response roots. Bulk rows, files, UI/auth/browser work, live qualification, and
coverage-complete claims remain outside the slice.

## Delegation decision

This product is a separable, multi-file implementation with real test and
coverage-generator work, so it belongs to one focused `codex-power` leaf. The
module, its tests, server registration, and generated coverage state are tightly
coupled; splitting them would introduce unnecessary cross-branch integration.
A fresh `grok` product review is necessarily sequential because it must inspect
the merged root product bytes.

## Execution

1. First commit the existing Grok research handoff record, current memory, and
   both iteration plans so the leaf starts from a reproducible root baseline.
2. Initialise `wave5i_sales_tax_account_meta_product` from
   `main.billy_complete` with `--agent=codex-power`, a bounded leaf profile
   (`--max-iters=8`, no descendants, 20-minute step timeout), and exclusive
   ownership of:
   - `src/billy_mcp/api/sales_tax_account_meta_writes.py`;
   - `src/billy_mcp/server.py` registration only;
   - `tests/api/test_sales_tax_account_meta_writes.py`;
   - `tests/api/test_sales_tax_account_meta_cross_executor.py`;
   - `tests/unit/test_coverage_server.py` Wave-5i registry assertion;
   - `scripts/generate_coverage_report.py` mappings and generated coverage
     artifacts for these six rows only.
3. The leaf implements all twelve real typed FastMCP tools and offline suites:
   exact `POST`/`PUT`/bodyless `DELETE`, encoded paths, update id equality,
   primary-root response parsing, optional deleted metadata, no retry, and all
   ticket tamper/expiry/replay/organisation/target/payload/effect/executor
   checks. It keeps inner `salesTaxAccount` and `salesTaxMetaField` maps opaque
   and must not modify the accepted Wave-5g sales-tax module.
4. The leaf runs focused contract and cross-executor tests plus the repository
   formatting, lint, type, coverage/policy, and non-live test gates. Only after
   real suites pass may it advance exactly six inventory rows to
   `implemented: true` and `contract_tested: true`; live stays zero, UI/vision
   and the 92 bulk rows remain red, and `complete` remains false.
5. Root reviews the clean three-dot diff, merges the leaf with a labelled
   no-fast-forward merge, re-runs root checks, and confirms the targets: 220
   `api_*` tools, 157 offline implemented/contract-tested API rows, and 52
   remaining clear CUD rows.
6. After that merge, launch a fresh `--agent=grok` independent product-review
   leaf owning only `wiki/wave_fivei_product_independent_review.md`. It must
   recheck current official documentation and product bytes, issue ACCEPT or
   REJECT, and preserve fail-closed live/UI/bulk status. A review refusal or
   authentication failure never counts as acceptance.

## Acceptance boundary

This iteration prepares and delegates one offline product cohort. It does not
claim live API, UI, browser, vision, bulk, file upload, special-route, or
overall-completeness qualification. The post-merge Grok review is a mandatory
gate before the product cohort can be accepted.
