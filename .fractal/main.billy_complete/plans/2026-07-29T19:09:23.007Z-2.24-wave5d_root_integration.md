# 2.24 Wave-5d Root Integration

## Objective

Integrate the already-frozen invoice and invoice-line singular CUD modules
only after both active Codex Power leaves commit their scoped work. Register
the twelve resulting ticketed tools on the root server, add root-owned
cross-executor and coverage evidence, and obtain the mandatory independent
Grok product verdict. The expected offline state is 166 `api_*` tools and 130
implemented/contract-tested API rows; live/UI/vision/bulk/special coverage and
`complete: false` must remain unchanged.

## Evidence and current state

- The accepted Wave-5d contract is
  `wiki/wave_fived_ticketed_writes_contract.md`; the freeze-only independent
  review is `wiki/wave_fived_freeze_independent_review.md`.
- The fresh cited Grok brief at `tmp/grok-research.md` reconfirms the official
  documentation fingerprint and explicitly keeps the Wave-5e bill cohort
  closed until this product integration is accepted.
- The root has an uncommitted, substantive update to `memory/state.md` that
  records the current research boundary. Preserve it through validation and
  commit it with the integration; do not discard it as stale scratch.
- `wave5d_invoice_writes` and `wave5d_invoice_line_writes` are active and
  report passing scoped tests, but their branches currently contain no
  implementation commit. Root must never copy their uncommitted files.

## Delegation decision

No new implementation child is appropriate. The only separable production
work is already exclusively owned by the two active Codex Power leaves.
Root-owned registration, cross-module ticket testing, coverage generation, and
integration verification all depend on both committed modules. After a clean
root integration, start a focused `grok` product-review child against the
committed tree; a Codex fallback review may document an unavailable Grok route
but cannot open the Wave-5e gate.

## Execution

1. Monitor both leaves through their contract review and commit. For each
   candidate branch, inspect `git diff main.billy_complete...<branch>` and
   verify the focused executable artifacts from a clean archive before merging
   with labelled `--no-ff` commits. Reject seed-only, out-of-scope, or
   uncommitted delivery.
2. Add root-only imports and calls for
   `register_invoice_write_tools` and `register_invoice_line_write_tools` in
   `src/billy_mcp/server.py`, reusing its one existing `WriteProtocolService`.
   Do not create a second confirmation store or alter the shared protocol.
3. Create `tests/api/test_invoice_cross_executor.py`, modelled on the accepted
   daybook-transaction cross-executor test. It must prove invoice-to-line and
   line-to-invoice ticket misuse returns `CONFIRMATION_MISMATCH` before
   consumption or HTTP, then prove each original ticket remains executable.
4. Update the root registry assertion in
   `tests/unit/test_coverage_server.py` to include both twelve-tool registrar
   sets and assert 166 `api_*` tools. Add exactly the six invoice/invoice-line
   CUD rows to `OFFLINE_API_IMPLEMENTATION_EVIDENCE` in
   `scripts/generate_coverage_report.py`, referencing the leaf-focused tests
   plus the server registry test. Generate rather than hand-edit coverage
   artifacts and confirm 130 offline rows with zero live rows.
5. Run formatter, Ruff, Pyright, coverage generator/inventory/policy checks,
   both leaf test modules, the new cross-executor test, confirmation and write
   protocol tests, coverage-server/inventory tests, and the complete non-live
   suite. Confirm the repository contains no secret or browser-evidence
   material and the test organisation was not touched.
6. Request the independent Grok product review of the committed root. It must
   check exact routes/roots, line multi-root mapping, strict outer models,
   execute-name binding, ticket mismatch/replay/expiry behaviour, zero write
   retry, registry/evidence arithmetic, generated coverage, and fail-closed
   posture. Record the non-sensitive verdict in the project wiki. Do not begin
   Wave-5e unless that verdict is ACCEPT.

## Non-goals

Do not implement bills or bill lines, bulk operations, specials, files,
attachments, UI/browser workflows, live qualification, or coverage completion.
No coverage row becomes live-tested or vision-verified in this integration.
