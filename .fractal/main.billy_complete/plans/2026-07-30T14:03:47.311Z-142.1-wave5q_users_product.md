# 142.1 Wave-5q users update product

## Decision

Implement the now-authorised `api.users.update` offline slice through one
focused `codex-power` child, `wave5q_users_product`. The API module, its
registration, the coverage generator, and its contract tests form one atomic
surface; splitting them would create needless server/coverage conflicts. The
current official-doc brief is cited in
`wiki/wave_fiveq_users_product_implementation_research.md`, and the separate
Grok freeze review is ACCEPT on the root branch, so no additional contract
research is required before this implementation leaf starts.

## Root baseline before spawning

1. Commit the Research72 handoff, its shared-wiki entry, and current memory so
   the child forks the cited contract rather than an uncommitted workspace.
2. Configure and start `wave5q_users_product` with `--agent=codex-power`, a
   childless leaf profile, and explicit file ownership in its `NODE.md`.
3. Monitor the leaf and merge only its reviewed, complete product output.

## Child contract

The child may own only these product artifacts (plus its own node directory):

| Path | Required result |
| --- | --- |
| `src/billy_mcp/api/user_writes.py` | New update-only typed preview/execute pair using `WriteProtocolService`. |
| `tests/api/test_user_writes.py` | Local contract tests for exactly the two tools and their write safety boundary. |
| `src/billy_mcp/server.py` | Register `register_user_write_tools` exactly once. |
| `scripts/generate_coverage_report.py` | Add the one `api.users.update` offline evidence mapping. |
| `coverage/api_v2_manifest.yaml`, `coverage/status.json`, `coverage/report.md` | Generated output only: one row changes to implemented + contract-tested; live remains false. |
| `tests/unit/test_coverage_server.py` | Assert the two registered users-update tools and API count 262. |

Contract limits:

- Only `api_users_update_preview` and `api_users_update_execute`; no user
  create/delete/bulk, generic transport, UI, browser, live, or vision work.
- Client-relative `PUT /users/:id`, outer strict `{id, user}` input, opaque
  `user` map, and optional `user.id == id` validation.
- Preview must be mutation-free. Execute accepts only the confirmation ticket,
  uses one no-retry HTTP write, and returns only the required `users` root.
- Keep high-sensitivity user values and tickets out of logs; do not claim
  privilege flags are writable or cleanup is live-qualified.
- Expected offline arithmetic is 177 → 178 implemented/contract-tested rows
  and 260 → 262 API tools; `complete`, UI, live, vision, and bulk rows remain
  red.

## Verification and follow-up

The child must run formatting, lint, Pyright, coverage-policy/repository-policy
checks, and the non-live test suite before committing. After a clean merge, the
root will regenerate/lint the wiki and coverage output, rerun the same checks,
then open a separate Grok product independent-review leaf. That review is a
post-merge gate; it must not be pre-authorised as an implementation outcome.
