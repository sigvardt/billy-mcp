Encode the cited Grok research96 residual unauthenticated-result facts and the
server-stated bulk-delete query form as fail-closed, offline-only harness
fixtures. This slice must not add an API/UI tool, real residual or bulk method
traffic, coverage greening, a browser flow, or an alternate organisation path.

  `.fractal/main.billy_complete/tmp/grok-research.md`; its primary source is
  the byte-identical current official Billy API page (ETag
  `wcw4x9hqvu3603`, MD5 `8b94b0135c91fd15fe54ea33e088a4be`).

  `400 INVALID_DELETE_ID_ARRAY`, while a synthetic id's unauthenticated
  meta-only `200` is never a non-persistence proof.

  `DELETE /{resource}?ids[]=123&ids[]=456`. JSON and form request bodies are
  rejected and are not product paths.

  residual creates/updates are `405`; bankPayments delete is `405`;
  transactions create/update are `401` and delete is meta-only `200`;
  invoiceReminderAssociations singular delete is meta-only `200`.

  `/organizations` is `401`; an invalid-token `401` is auth-first and cannot
  prove either path. The existing documentation-path tool is unchanged until a
  valid dedicated non-production token resolves the ambiguity.
- The current dirty memory and shared-wiki changes are the adopted Research96
  relay. They must be committed as a parent checkpoint before the child is
  started, so the child inherits durable non-sensitive evidence.

## Delegation decision

This is a bounded repository implementation with one tightly coupled source
and test pair, so a focused `codex-power` leaf owns exactly
`src/billy_mcp/live_probe.py` and `tests/unit/test_live_probe.py`. Splitting
the two files would create unnecessary contract conflicts. No new Grok research
leaf is needed before coding because Research96 is already a cited Grok brief.
After the implementation is merged and parent-verified, a separate `grok`
review leaf will own only a new non-sensitive project-wiki review record; it
must not accept residual/bulk product tools or change coverage.
