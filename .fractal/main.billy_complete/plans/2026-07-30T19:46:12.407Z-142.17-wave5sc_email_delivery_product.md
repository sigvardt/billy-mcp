# 142.17 Wave-5s-C ticketed email and delivery product

## Objective

Land the newly completed Grok research86 handoff as the immutable baseline, then
delegate the bounded four-tool Wave-5s-C API product slice to Codex Power:

- `api_invoices_send_email_preview` / `api_invoices_send_email_execute`
- `api_invoice_deliveries_create_preview` / `api_invoice_deliveries_create_execute`

The scope is intentionally offline-only. Both API inventory rows may become
implemented and contract-tested only after passing real contract tests; all
live, UI, vision, residual-clear, and bulk rows remain red.

## Adopted contract and gate

- `wiki/wave_fivesc_research86_product_implementation_handoff.md` is the
  current cited official-doc handoff. It reconfirms the public API body as MD5
  `8b94b0135c91fd15fe54ea33e088a4be` and opens the product gate only after the
  accepted containment-repaired upload.
- Email is a high-side-effect `POST /v2/invoices/{invoiceId}/emails` with
  `{email: ...}`. Its ticket binds the invoice target and canonical email body;
  no raw destination, multi-recipient, destination URL, webhook, or retry.
- E-invoice delivery is a high-side-effect `POST /v2/invoiceDeliveries` with
  `{invoiceDelivery: ...}`. It binds payload organisation and invoice target;
  only `gln` or `cvr` are valid receiver types, GLN requires exactly 13 digits,
  and no `receiverCvr` or nested invoice route may be invented.
- The generic write protocol cannot safely model these special response roots
  and target bindings. The implementation must follow the custom
  `ConfirmationStore` service pattern of `file_upload_writes.py`.

## Delegation decision

Spawn one `codex-power` leaf after committing the research baseline. The email
and delivery tools share custom confirmation lifecycle conventions, server
registration, focused test support, and exactly two manifest rows; splitting
them would create avoidable conflicts in those shared files. A separate Grok
independent product review remains a clean-context task, but can start only
after the product has been merged and independently verified on root.

The leaf owns only:

- `src/billy_mcp/api/invoice_email_delivery_writes.py`
- `tests/api/test_invoice_email_delivery_writes.py`
- `src/billy_mcp/server.py` registration for this module
- the two special rows in `coverage/api_v2_manifest.yaml` and any generated
  coverage artifact required by the repository's generator

It must not modify uploads, generic write protocol, invoice-log reads, client
allowlists, UI inventory, bulk rows, or residual clear rows.

## Execution plan

1. Validate and commit the already-written research86 wiki page, refreshed
   wiki index, and present-tense memory update. Run both wiki lints and the
   repository's relevant non-code safety checks so the child forks a clean,
   cited baseline.
2. Initialise `wave5sc_email_delivery_product` with `--agent=codex-power`, a
   leaf-only depth/child configuration, and explicit file ownership in its
   `NODE.md`. Commit its seed and start it only after the root baseline commit.
3. Direct the child to implement strict Pydantic preview and ticket-only execute
   models; bind tool, organisation, target, canonical request, expected effect,
   and expiry; consume each ticket before the single external POST; and map
   unknown response envelopes to typed errors.
4. Require focused contract tests for tool schemas, no-preview HTTP, exact URL
   and JSON, validation, ticket tampering/replay/expiry/tool-org-target-payload
   mismatch, base-URL lock, no retry, and recursive redaction of email subject
   and body. Coverage evidence must name the focused test suite and retain
   `live_tested: false`.
5. On child completion, verify its committed bytes from a clean archive, merge
   with a labelled no-fast-forward merge, regenerate and lint the project wiki,
   and run the focused tests plus root format, lint, type, coverage, policy,
   and credential checks.
6. Only then start a fresh Grok independent product-review leaf. Its verdict
   must explicitly distinguish offline acceptance from live/UI/vision/
   completeness qualification; a failed pre-edit Grok run may be retried once
   with Codex Power as a non-authoritative fallback under the routing policy.
