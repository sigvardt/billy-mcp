# 142.11 Wave-5s-B files upload product

## Objective

Land the next bounded offline API write slice: the typed, ticketed binary
`api_files_upload_preview` and `api_files_upload_execute` tools for documented
`POST /v2/files`. The product must use the cited Grok research80 handoff as its
contract, preserve all fail-closed coverage boundaries, and not make a live,
UI, vision, bulk, webhook, or completeness claim.

## Adopted state and authority

- The dirty worktree is an intentional, reviewable research80 handoff: the
  cited page `wiki/wave_fivesb_files_upload_product_ready_research.md`, its
  project-memory update, and supporting research-plan record. Its scratch brief
  is `.fractal/main.billy_complete/tmp/grok-research.md`.
- Research80 records the current official-doc fingerprint (MD5
  `8b94b0135c91fd15fe54ea33e088a4be`) and locks binary-only `POST /files` on
  `https://api.billysbilling.com/v2`. It explicitly prohibits a JSON
  `api_files_create*` family and treats `api.files.create` as the empty-tool
  alias of `api.special.files_upload`.
- The merged invoiceLogs Codex fallback review is an offline-only acceptance;
  it and the still-active files-upload fallback review do not replace the
  mandatory post-product Grok audit. The research80 Grok brief is nevertheless
  the required cited research input for this Codex Power implementation.

## Delegation decision

This is a separable implementation with its own client extension, direct
file-identity ticket protocol, FastMCP registration, manifest generation, and
contract tests. It warrants one focused `codex-power` leaf after the research
baseline is committed. No parallel implementation leaf is safe because the
same tool count, server registration, client, coverage evidence map, and new
test suite must evolve together. The active fallback reviewer remains
independent and is not given product ownership.

## Execute sequence

1. Inspect the completed files-upload Codex fallback review (`b00adec`) and,
   after confirming it is review-only, merge its limited review record with the
   standard labelled merge. Its ACCEPT may inform offline quality but does not
   replace the Grok audit or gate the research80-led product leaf.
2. Inspect the concurrent research80 changes against the scratch brief and
   repair only the three orphan trailing `)` artifacts in its wiki page,
   root-memory state page, and supporting research-plan page. Run `wiki update`
   and `wiki lint` for the project wiki, preserve all research non-claims, and
   commit this baseline before creating a child.
3. Initialise a leaf from that committed baseline, explicitly routed with
   `--agent=codex-power`, named `wave5sb_files_upload_product`, with no child
   depth/width/descendants. Configure its `NODE.md` to own only:
   `src/billy_mcp/api/file_upload_writes.py` (new), the narrow binary method in
   `src/billy_mcp/client.py`, upload registration in `src/billy_mcp/server.py`,
   `scripts/generate_coverage_report.py`, the generated coverage files,
   `tests/api/test_file_upload_writes.py` (new), and the exact registry and
   coverage assertions needed for that tool family. It must escalate any need
   to alter attachment JSON writes, file reads, confirmation-store semantics,
   or the frozen dual-row inventory contract.
4. The leaf must implement direct `ConfirmationStore` binding, not the JSON
   `WriteProtocolService`: preview resolves under non-empty `BILLY_UPLOAD_ROOTS`,
   requires a regular file, records canonical resolved path, SHA-256, size, and
   `mtime_ns`, and performs no HTTP. Execute accepts only the ticket,
   consumes it once, re-resolves/revalidates every bound identity field, then
   calls a narrow no-retry binary `POST /files` client method. It must return
   `FILE_NOT_ALLOWED` for outside/missing/non-regular paths and `FILE_CHANGED`
   for changed path, size, mtime, or digest; it must never retain raw bytes in
   tickets or logs.
5. The client method must accept only a relative Billy route and exact
   allowlisted headers: internally injected token and JSON accept header,
   required `X-Filename` and `Content-Type`, and only optional
   `x-create-attachment`, `x-create-variants`, `x-organizationid`, and
   `x-should-scan`. It may not expose generic headers, alternate URLs,
   multipart/streaming control, retries, or JSON upload creation. Success maps
   opaque `files[]` and optional `attachments[]`; `downloadUrl` remains
   redacted.
6. Require focused tests for no preview HTTP, root and regular-file rejection,
   binary body/header exactness, optional-header omission and lowercase
   `"true"`, file mutation (content, size, mtime, and path), expiry, replay,
   tampering/cross-executor mismatch, un-retried upstream failure, foreign URL
   rejection, strict FastMCP schemas, success-root validation, and redaction.
   Update the registry expectation from 265 to 267 `api_*` tools while asserting
   that no `api_files_create*` tool exists.
7. Only after these tests exist, add evidence for both
   `api.special.files_upload` and `api.files.create` to
   `OFFLINE_API_IMPLEMENTATION_EVIDENCE`, regenerate the maintained coverage
   artifacts, and prove the offline count changes from 180 to 182 implemented
   and contract-tested rows. Keep both live-tested rows false, all UI rows red,
   the 92 bulk rows red, and `complete: false`.
8. Monitor the leaf through radio and `fractal node list`. On completion,
   inspect its three-dot diff and clean-archive tests before a labelled
   `git merge --no-ff -m "merge main.billy_complete.wave5sb_files_upload_product"`.
   Then commission a new, independent Grok product-review leaf; an
   authentication-failed Grok leaf is not acceptance evidence and may only
   trigger the prescribed pre-edit fallback retry.

## Verification gates

- Research baseline: `git diff --check`, project `wiki lint`, documentation
  structure, credential scan, and the existing non-live suite all pass before
  spawning.
- Product leaf: Ruff, Pyright, focused upload/client/coverage/registry tests,
  coverage generation and false-completeness guard pass from a clean archive.
  The explicit `--require-complete` check must still fail for the documented
  live/UI/bulk gates.
- No API token, browser credentials, live HTTP write, screenshot, HAR, trace,
  uploaded customer data, or raw file bytes may enter the repository or test
  output. The leaf does not claim cleanup qualification because singular file
  DELETE is method-closed and attachment deletion remains live-gated.

## Expected outcome

At most, this cycle produces a production-quality offline implementation and
contract evidence for the two inventory rows. It does not produce product
acceptance or a completed project; live API qualification, interface parity,
vision review, bulk resolution, and the mandatory independent Grok product
review remain distinct gates.

## Post-Mortem

The cited research80 handoff was committed and independently accepted by Grok
as an offline implementation input, with no blocking contract finding. The
focused Codex Power leaf was launched for the binary upload implementation.
Its inherited Grok research stage failed before edits because that agent was
not authenticated; it was stopped, rerouted to Codex Power, and restarted using
the accepted cited handoff rather than unsupported fresh research. Baseline
verification passed (1180 non-live tests, lint, type checking, coverage and
repository-policy checks, and dependency audit). Product integration, the
post-product Grok review, live/UI/vision evidence, and all bulk rows remain
unresolved.
