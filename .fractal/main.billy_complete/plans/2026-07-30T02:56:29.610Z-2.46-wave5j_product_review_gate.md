# 2.46 Wave-5j product review gate and Wave-5k sequencing

## Objective

Obtain an independent Grok verdict on the merged Wave-5j bank-line ticketed
write product before any Wave-5k authoring. Preserve the current cited
bankPayments research handoff without interpreting it as a product or coverage
acceptance.

## Adopted evidence and current state

- Root merge `d86844f` contains `bank_line_writes.py`, the frozen eighteen
  preview/execute handlers, and the associated offline tests. The archive
  verification of the committed candidate passed 59 focused tests.
- The frozen authority is `wiki/wave_fivej_ticketed_writes_contract.md`, plus
  the accepted freeze and product-readiness reviews already recorded in the
  project wiki.
- Research46 in `.fractal/main.billy_complete/tmp/grok-research.md` reconfirms
  the official API fingerprint and the Wave-5k bankPayments boundary. It is a
  cited research brief only: it makes no coverage, live, UI, or vision claim.
- Root remains at 238 `api_*` tools and 166 implemented/contract-tested API
  rows, with all live and vision counts at zero and `complete: false`.

## Delegation decision

The required product acceptance is an independent audit of a substantial,
already-merged code and test delta. It is both separable from future
implementation and explicitly owned by Grok, so a focused leaf is warranted.
No Wave-5k implementation child will be launched in parallel because its
freeze authoring is expressly gated on this review's ACCEPT verdict.

## Execution plan

1. Commit the adopted research46 memory and readiness-plan records with this
   plan so the reviewer forks the actual merged root evidence.
2. Initialize and configure `wave5j_product_review` as a child routed to
   `grok`. Its sole deliverable is a cited, non-sensitive
   `wiki/wave_fivej_product_independent_review.md` with ACCEPT or REJECT.
   It must inspect the committed root bytes, run the relevant offline tests,
   compare all 18 tool names, methods, roots, ticket binding, response mapping,
   error mapping, retry behavior, registry, and inventory updates against the
   frozen contract, and reject any broadened bankPayments/bulk/UI/live claim.
3. Launch and monitor that reviewer. On REJECT, route only identified fixes to
   a `codex-power` implementation leaf and require re-review. On ACCEPT, merge
   the review page and then, in a later gated plan, authorize a separate
   `codex-power` Wave-5k freeze-page authoring leaf from research46 section
   5.1. Do not start either future child during this gate.

## Success criteria for this iteration

- The current research and state records are durable without credentials or raw
  probe artifacts.
- The Grok reviewer is configured against the merged root and its acceptance
  conditions are objectively satisfiable from its own committed deliverable.
- No coverage flag, live/UI/vision claim, or Wave-5k tool changes before the
  independent verdict.
