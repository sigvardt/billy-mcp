# 1.1 Wave-5s-B files upload product

## Scope decision

This node is a leaf (`max_depth`, `max_children`, and `max_descendants` are all
zero), so no delegation is possible. Implement one bounded offline slice only,
using the accepted research brief and no external discovery.

## Deliverable plan

1. Add the narrow `BillyHttpClient` binary upload operation for exactly
   relative `/files`. Validate only the documented filename/content-type and
   four optional header inputs, create the client-owned token and accept
   headers, send raw bytes once, preserve locked-host/error parsing/redaction,
   and keep retry policy at zero for the POST path. Extend the existing client
   test module only where needed.
2. Create `api/file_upload_writes.py` as a dedicated service—not a
   `WriteProtocolService` route. Define strict Pydantic preview/execute input
   and typed result models. Preview canonically resolves a configured-root
   regular file and stores only path/identity/options in an opaque
   `ConfirmationStore` binding plus volatile prepared metadata. Put SHA-256,
   size, and `mtime_ns` in the canonical request/binding; retain no bytes.
   Execute accepts just the ticket, verifies the exact upload executor, consumes
   it through the unmodified store, re-resolves/re-hashes before one byte read,
   and maps local validation or documented response-root errors stably.
3. Register only `api_files_upload_preview` and `api_files_upload_execute` in
   the root server, sharing its client, app config, and confirmation store.
   Leave file reads and attachment JSON writes untouched. Add the two generated
   evidence-map entries and the minimal registry/coverage assertions, then
   regenerate `coverage/`; confirm alias `api.files.create` remains tool-less.
4. Add `tests/api/test_file_upload_writes.py` with local temp files and mock
   transport: flat strict schemas/registration, no preview HTTP, configured
   roots/nonregular rejection, ticket expiry/replay/tamper/wrong-executor
   handling, all identity drifts, exact raw bytes/headers and optional-header
   omission, malformed success roots, redaction, locked path/host rejection,
   no retry, and both evidence rows.
5. Run formatting, focused tests, full non-live suite, Ruff, Pyright, coverage
   generation plus false-completeness checks, policy credential scan, and
   dependency audit. Treat `--require-complete` failing for live/UI/bulk gates
   as expected. Update memory, report the result, and commit only after every
   required check is accounted for.

## Safety invariants

- No `api_files_create*`, JSON upload/create body, generic headers/path/host,
  multipart/streaming surface, raw file bytes in ticket/output/logs, browser,
  credentials, or live requests.
- `ConfirmationStore` semantics remain unchanged. If its existing opaque-store
  API cannot express a required ticket result without changing the store,
  stop and escalate rather than widening scope.
- The target inventory state is 182 implemented and contract-tested API rows,
  267 API tools, zero live/vision rows, 92 red bulk rows, and `complete: false`.
